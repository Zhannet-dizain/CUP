Техническое задание: Fleet Vision AI

Стек: Flutter (Dart), поддержка Web/Desktop/Mobile, State Management (Riverpod), Backend (Supabase/Firebase).

1. Общие требования и Архитектура

Архитектура: Clean Architecture (разделение на слои data, domain, presentation).

Принцип UI: «Контроль за 10 секунд» (яркое цветовое кодирование, минимум кликов для смены статуса, критические риски видны сразу).

Логирование: Любое изменение статуса ТС должно записываться в таблицу истории status_history.

2. Модель данных ТС (Vehicle Model)

Каждый объект ТС должен содержать следующие поля:

id (String/UUID) — уникальный идентификатор

licensePlate (String) — госномер

brandModel (String) — марка и модель

trailer (String?) — прицеп (опционально)

driver (String?) — ФИО водителя (опционально)

column (String) — колонна / филиал

status (VehicleStatus) — текущий статус (enum)

statusDuration (Duration) — длительность текущего статуса

reason (StatusReason?) — стандартизированная причина статуса (enum/справочник)

location (String) — геопозиция / местоположение

responsibleUser (String) — ответственный сотрудник (роль/ФИО)

comment (String?) — текстовый комментарий

lastUpdated (DateTime) — дата и время последнего изменения

5. Дорожная карта реализации MVP

Шаг 1: Базовая структура и Модели (Разрабатывает Jules AI)

Создать папки по Clean Architecture: lib/features/fleet/data, lib/features/fleet/domain, lib/features/fleet/presentation.

Описать класс Vehicle со всеми enums (VehicleStatus, StatusReason).

Реализовать локальный репозиторий с mock-данными для тестирования интерфейса.

Шаг 2: UI - Главный экран (Dashboard)

Реализовать два режима отображения: Таблица (scannable table) и Сетка карточек (grid cards).

Вывести дашборд с ключевыми KPI сверху:

Всего ТС, В пути, В ремонте, В простое.

Список машин с критическим временем простоя (> 4 часов без обновлений).

Добавить панель быстрых фильтров (по статусу, колонне, водителю).

Шаг 3: Модальное окно изменения статуса (10-second rule)

Клик по машине -> Быстрое меню -> Выбор нового статуса в 2 клика.

Если статус требует подтверждения (например, "ДТП" или "Ремонт"), открывать поля для прикрепления фото/документа и выбора стандартизированной причины.

Шаг 4: История изменений

Реализовать экран истории изменений для конкретного ТС.

Каждая запись должна содержать: timestamp, author, oldStatus, newStatus, reason, attachments (фото/файлы).

6. Перспективные интеграции (Фаза 2)

Синхронизация с 1С:Управление автотранспортом (УАТ).

API-интеграция с телематикой ГЛОНАСС/GPS система СКАУТ для автоматического обновления координат и статуса движения.

Система авто-уведомлений в MAX-мессенджер (Webhooks).
